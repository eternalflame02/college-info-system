\begin{center}
  {\Large \textbf{Abstract}}\\[0.5cm]
\end{center}
\setstretch{1.5}

Finding specific academic details on college websites is often a frustrating experience because the data is usually unstructured and spread across many different pages. Standard keyword searches frequently miss the mark when handling this kind of scattered content. To address this, we built a hybrid knowledge-graph-enhanced retrieval-augmented generation (KG-RAG) system for the MBCET CSE department website.

\par
The pipeline begins by collecting web pages and PDF documents, then breaking them into semantic chunks. We generate 768-dimensional vectors for each chunk using EmbeddingGemma and store these in ChromaDB. Alongside that, we construct a lightweight knowledge graph to model connections between faculty, courses, programs, and semesters. The graph records deterministic, evidence-backed relationships such as \textit{teaches} and \textit{part\_of}, and it also allows schema support for \textit{has\_prerequisite}. When a user asks a question, the router tries to identify the query type and then chooses semantic retrieval, graph traversal, or a bit of both. The retrieved material becomes the grounded context for a large language model to generate a final answer.

\par
Right now, the pipeline indexes 2207 semantic chunks, with 195 from HTML and 2012 from PDFs. It has ingested 2268 vector documents into ChromaDB, including 61 synthetic documents derived from the knowledge graph. We also validated a 480-node academic graph to check data integrity. Based on our evaluation, this hybrid setup appears to improve factual accuracy in most cases when compared to RAG systems that depend only on embeddings, though some cases still need further tuning~\cite{kg_rag_springer,rag_edu_elsevier}.

\par
\noindent\textbf{Keywords:} Retrieval-Augmented Generation, Knowledge Graph, Vector Embeddings, Semantic Chunking, ChromaDB, Academic Information Systems.

\chapter{Introduction}

Higher education has largely moved online, turning college websites into the main way students, parents, and faculty interact with institutions. However, we often find this information painfully scattered. Important details end up unstructured and are rarely organised in one logical place. For instance, course syllabi sit inside separate PDF downloads. Faculty profiles hide away in nested department pages, and academic rules keep changing across multiple revised documents. Trying to find what you need becomes incredibly tedious under these conditions.

\par
Usual search tools and built-in site engines rarely solve this frustration. They generally rely on exact keyword matches, meaning they fail if a user frames their question differently from the source text. If a student types ``who teaches Artificial Intelligence'', an old-school lookup will completely ignore a timetable PDF that only lists a course code. People working in information retrieval know this semantic gap between what we mean and what is written is quite difficult to bridge~\cite{kg_rag_springer}.

\par
Retrieval-Augmented Generation (RAG) tackles a good portion of the issue. We can use it to combine semantic vector matching with the reasoning abilities of large language models (LLMs). When someone asks a question, a RAG setup converts the query into a vector representation to find the most relevant document chunks. We then feed these chunks into an LLM to generate an answer based purely on the retrieved facts. Because it grounds the model in actual documents, this method heavily cuts down on hallucinations and looks very promising for educational tools~\cite{rag_edu_elsevier}.

\par
Unfortunately, relying exclusively on vector embeddings does have a major downside. Standard RAG systems look at text passages completely in isolation. They miss the broader \textit{structural relationships} that connect different academic subjects together. By its very nature, a college system is entirely relational. Certain courses fit into specific degree programs, while professors cover distinct classes. You need these links to successfully handle a multi-hop query like ``Which professors in CSE teach semester~5 courses?'' or ``What are the prerequisites for the elective on Machine Learning?'' A knowledge graph (KG) solves this by mapping things out as nodes and edges. It explicitly models these boundaries, allowing graph-based logic to work alongside semantic similarity lookups. Recent papers verify that bringing KGs into RAG setups leads to much higher accuracy on complex questions, better factual anchoring, and results that are much easier to verify~\cite{kg_rag_springer}.

\par
To test these ideas, we propose a \textbf{hybrid knowledge-graph-enhanced retrieval-augmented generation system} targeted entirely at academic portals. Our project hones in on the Computer Science and Engineering (CSE) department at Mar Baselios College of Engineering and Technology (MBCET). We engineered a full end-to-end pipeline that scrapes the college website, pulls content from PDFs, breaks text into semantic chunks, and creates vector embeddings. Crucially, we also build a connected knowledge graph and route user questions intelligently. At this stage, we have indexed 2207 semantic chunks and constructed a highly reliable knowledge graph backed entirely by source evidence. By putting these pieces together, we provide context-aware, relationally grounded answers to students and faculty searching for academic data.

\chapter{Literature Review}

This chapter examines the major studies bridging retrieval-augmented generation, knowledge graphs, and educational data systems. These works heavily influenced the design choices in our hybrid KG-RAG framework.

\par
The foundational formulation of RAG was introduced by Lewis~\textit{et al.}~\cite{lewis2020}, who established that coupling a pre-trained language generator with a Dense Passage Retriever significantly reduces hallucination in knowledge-intensive NLP tasks. Building on this to handle broader contexts, Izacard and Grave~\cite{izacard2021} presented the Fusion-in-Decoder architecture, demonstrating that independently encoding retrieved passages yields superior accuracy for multi-document question answering. Furthermore, the modern trajectory of synthesizing structured logic with raw generation is explored comprehensively by Pan~\textit{et al.}~\cite{pan2024}; their roadmap survey explicitly identifies the KG-enhanced LLM paradigm as the superior mechanism for factual anchoring—a philosophy strictly adopted in this project.

\par
In the context of architectural deployments, Linders and Tomczak~\cite{kg_rag_springer} engineered a knowledge-graph-extended RAG framework proving that standard similarity retrieval can be substantially augmented using deterministic graph-guided entity relationship traversal, a technique crucial for unlocking accurate multi-hop QA. Finally, applying these paradigms to academic institutions, Li~\textit{et al.}~\cite{rag_edu_elsevier} provided an extensive survey isolating RAG's impact inside educational boundaries. Their findings confirm that isolated, domain-specific semantic engines massively outperform general-purpose models on institutional datasets, but critically identify the fundamental lack of structured, entity-level relational data as the primary failure point in academic deployment, explicitly validating our implementation of a hybrid KG-RAG pipeline.

\chapter{Proposed Methodology}

\section{Problem Statement}

Students and parents trying to dig up academic information on college portals often hit a wall of unstructured, disorganized, and fragmented webpages. Normal keyword searches break down completely here because the words a student types simply do not align with the formal academic language used in the documents. While pulling in RAG has proven excellent at locking LLMs to true facts, depending strictly on embeddings completely misses the hidden web of connections between different parts of a college. It cannot easily infer how departments, subjects, and teachers link together, which generally leaves the responses feeling vague or completely disconnected from the query.

\par
The central challenge for this mini project boils down to this: \textit{Given a natural-language question about college details, how do we successfully locate and blend the right semantic document chunks alongside the structural logic of a knowledge graph mapping academic entities?}

\par
To make that happen, our build needs to: (a)~pull raw HTML and PDF content from the college domain and turn it into searchable semantic chunks; (b)~build a lightweight graph detailing the relationships linking faculty, classes, degree tracks, and semesters; (c)~figure out what the user was actually trying to ask, routing the prompt to the best retrieval engine (whether vector, graph, or both); and (d)~produce a clean, conversational answer completely restricted to the proven institutional facts it downloaded.

\subsection*{Objectives}

\begin{itemize}
  \item To collect academic data from the MBCET CSE department website using automated web scraping with BFS URL discovery, HTML-to-Markdown conversion, and PDF table extraction.
  \item To design and implement a semantic chunking pipeline that classifies content by type (profile, regulation, table, section, list) and preserves structural metadata.
  \item To generate vector embeddings using EmbeddingGemma (768-dimensional) and store them in ChromaDB for fast similarity-based retrieval.
  \item To construct a phase-1 knowledge graph with deterministic edges (teaches, part\_of, has\_prerequisite) backed by chunk-level evidence provenance.
  \item To implement an intent-aware query router that classifies queries into types (teaching, faculty, advisory, course, timetable, regulation, general) and routes them to the optimal retrieval path.
  \item To integrate the retrieved context with a large language model for grounded answer generation.
\end{itemize}

\subsection*{Scope}

We limited our data gathering to the MBCET CSE department website (\texttt{mbcet.ac.in}). At present, the scraping pipeline produces 2207 semantic chunks across tables, profiles, general sections, regulations, and lists. The knowledge graph captures 64 faculty profiles, 405 courses, 3 degree tracks, and 8 semester nodes, with deterministic logic governing every edge. For vectorisation, we use EmbeddingGemma (768 dimensions) with a batch size of 64 and a 512-token sequence cap to keep it workable on a GTX 1650 Ti GPU with 4~GB VRAM. If that still runs out of memory, the pipeline falls back to CPU processing.

\section{Proposed Methodology}

The proposed system is organised as a multi-stage pipeline. First, it gathers and cleans content. After that, it converts the content into vectors and graph entities. Finally, it routes queries and generates answers. We found this breakdown helpful, though the stages overlap in practice and required a few iterations to tune correctly. The main ideas are these: a semantic chunker that preserves metadata and entity links, a knowledge graph that only accepts high-confidence edges, and a router that adjusts retrieval strategy dynamically based on the query.

\subsection{Data Collection}

Gathering the raw files from the MBCET CSE department portal falls to a custom BFS-based URL discovery engine we coded in Python. The crawler employs the \texttt{requests} module and obeys rate limits with a 1.0-second delay between hits, trying heavily failing links three times while sending a polite user-agent header. Inside the engine, we split focus entirely on two formats:

\begin{itemize}
  \item \textbf{HTML Pages:} This covers the department's general overview, professor bios, lab configurations, program goals, and events. Our hook converts everything into neat Markdown blocks making use of \texttt{markdownify}, diligently removing messy HTML clutter and adjusting spacing.
  \item \textbf{PDF Documents:} Crucial curriculum items like B.Tech CSE, B.Tech AI, and M.Tech CSE syllabi reside in here alongside strict regulations (R2019, R2023), academic calendars, and exams schedules. We strip the plain text and complex tabular data formatting entirely via \texttt{pdfplumber}, falling back on Tesseract OCR if the scanner hits an image-based file.
\end{itemize}

\subsection{Semantic Chunking}

After producing Markdown, the semantic chunker converts the content into segments that preserve meaning. We avoided simple fixed-length splitting and kept the chunk boundaries aligned with natural structure:

\begin{itemize}
  \item Parses Markdown structure (headers, lists, tables, paragraphs) to identify natural semantic boundaries.
  \item Classifies each chunk into one of five content types: \textbf{profile} (faculty), \textbf{regulation}, \textbf{table} (course lists, timetables), \textbf{section} (general content), and \textbf{list}.
  \item Links chunks to entity references (e.g., faculty IDs, course codes, semester identifiers) for downstream knowledge graph integration.
  \item Enforces configurable chunk size constraints: minimum 80 words, preferred 450 words, soft limit 600 words, maximum 700 words.
  \item Performs SHA-256 based deduplication to eliminate redundant content.
\end{itemize}

  \centering

  \begin{tabular}{|l|l|p{6cm}|}

    \textbf{Field} & \textbf{Type} & \textbf{Description} \\ \hline

\subsection{Vector Embedding and Storage}

After generating individual semantic chunks, we pass them to the 768-dimensional \textbf{EmbeddingGemma} model (\texttt{google/embeddinggemma-300m}) using Sentence-Transformers. We apply L2 normalisation so cosine distances are comparable, and then we store the vectors in a persistent \textbf{ChromaDB} database.

\par
Key implementation details:
\begin{itemize}
  \item We use batch size 64 because it fits well on a 4~GB GTX 1650 Ti without exhausting GPU memory.
  \item Sequence length is capped at 512 tokens for performance; the model's full 2048-token mode slows down long table chunks by roughly 30$\times$.
  \item If CUDA runs out of memory, the code halves the batch size until it works. If batch size 1 still fails, it falls back to CPU computation.
  \item Embeddings are cached in compressed \texttt{.npz} files so we do not need to recompute them on every run.
  \item We keep structured metadata such as content type, section hierarchy, entity references, and source file alongside each vector to support filtered retrieval.
\end{itemize}

\subsection{Knowledge Graph Construction}

We built the knowledge graph to be deliberately lightweight for phase 1, avoiding the overhead of a graph database.

\begin{itemize}
  \item \textbf{Storage format:} The whole graph is stored as JSON.
  \item \textbf{Edge policy:} We only accept edges with confidence 1.0.
  \item \textbf{Evidence provenance:} Every edge records the source chunk ID, source file, and extraction rule.
\end{itemize}

\par
At this stage, the graph includes four node types and three edge relations:

\begin{table}[htbp]
  \centering
    \vspace*{5pt}
  \begin{tabular}{|l|l|p{6cm}|}
    \hline
    \textbf{Element} & \textbf{Type} & \textbf{Description} \\ \hline
    Node & Faculty   & 64 faculty members with name, aliases, URL     \\ \hline
    Node & Course    & Course code, name, credits, aliases             \\ \hline
    Node & Program   & B.Tech CSE, B.Tech AI, M.Tech CSE               \\ \hline
    Node & Semester  & Semesters 1--8 (deterministic from chunk refs)   \\ \hline
    Edge & teaches          & Faculty $\rightarrow$ Course (from timetable tables) \\ \hline
    Edge & part\_of          & Course $\rightarrow$ Program (from syllabus source)   \\ \hline
    Edge & has\_prerequisite & Course $\rightarrow$ Course (schema-supported; none extracted in current build)   \\ \hline
  \end{tabular}
  \caption{Knowledge Graph Node and Edge Types}
  \label{tab:kg_types}

\end{table}

Our logic for gathering relationships functions exclusively across three explicit rules targeting text formatting within the chunks:
\begin{enumerate}
  \item \textbf{Course-Projecting Maps:} Links labelled as \texttt{part\_of} tie program identifiers and semantic pieces holding course code entities together. It searches for specific co-occurrences of entities as well as checking the document name (such as mapping syllabus items featuring ``cse\_ai'' automatically to the B.Tech AI entity).
  \item \textbf{Prerequisite Finders:} Regular expression scripts hunt down strings annotated with \texttt{prerequisite:}, hooking the succeeding course strings to their appropriate node IDs.
  \item \textbf{Assignment Connections:} Timetable extraction works when faculty nicknames show up alongside course shortcuts natively connected by a pipe delimiter. It also pulls relationships out when text relies squarely on descriptive verbs like ``teaches'', ``handled by'', or ``instructor''.
\end{enumerate}

After building the graph in JSON, we validate every edge carefully. Confidence values must be 1.0, both endpoints must exist, deterministic flags must be true, and evidence fields cannot be empty.

\subsection{Hybrid Retrieval}

Once a query arrives, the pipeline first tries to identify user intent and then chooses the retrieval path.

\begin{enumerate}
  \item \textbf{Query classification:} The query is assigned to one of seven types: \textit{teaching}, \textit{faculty}, \textit{advisory}, \textit{course}, \textit{timetable}, \textit{regulation}, or \textit{general}.
  \item \textbf{Retrieval routing:} Based on this label, ChromaDB applies filters and adjusts the result count:
    \begin{itemize}
      \item \textit{teaching} $\rightarrow$ narrow to \texttt{knowledge\_graph} items, $k=5$
      \item \textit{faculty} $\rightarrow$ select \texttt{profile} chunks, $k=3$
      \item \textit{advisory} $\rightarrow$ focus on tables but allow some fallback, $k=10$
      \item \textit{course} $\rightarrow$ use \texttt{table} chunks, $k=10$
      \item \textit{timetable} $\rightarrow$ use \texttt{table} chunks, $k=5$
      \item \textit{regulation} $\rightarrow$ use \texttt{regulation} chunks only, $k=5$
      \item \textit{general} $\rightarrow$ no filter, $k=5$
    \end{itemize}
  \item \textbf{Adaptive distance thresholding:} We do not accept the top results blindly. The retrieval threshold changes depending on how strong the best match is:
    \begin{itemize}
      \item Best distance $< 0.3$: threshold = 0.6.
      \item Best distance 0.3--0.5: threshold = 0.7.
      \item Best distance $> 0.5$: threshold = 0.8, and the system may warn that the match is weak.
    \end{itemize}
\end{enumerate}

\subsection{Answer Generation}

The selected vectors and knowledge graph evidence are passed to a large language model. We instruct the model to use the provided context as the only source of facts and to say that the answer is not available if it cannot be supported. In practice, this helps reduce hallucinations, though it does not eliminate them entirely.
\subsection{Modules of the Project}

The system is divided into the following functional modules which correspond to the pipeline stages of the application:

\begin{enumerate}
  \item \textbf{URL Discovery Module (\path{scraper/url_discovery.py}):} A Breadth-First Search (BFS) crawling engine that discovers HTML pages and PDF links under the CSE department URL. It supports configurable depth limits and URL-pattern filtering (include/exclude paths).
  \item \textbf{HTML Scraper Module (\path{scraper/html_scraper.py}):} Handles HTML pages scraped from the department website. It converts discovered HTML to clean Markdown format and specifically extracts structured faculty lists by parsing nested DOM elements using BeautifulSoup4, with built-in error recovery mechanisms.
  \item \textbf{PDF Handler Module (\path{scraper/pdf_handler.py}):} A robust PDF processing stage utilizing \textit{pdfplumber} for text and tabular data extraction. For documents containing scanned pages, it features an OCR fallback mechanism via Tesseract to ensure high-fidelity extraction of academic syllabi and examination timetables.
  \item \textbf{Entity Registry Module (\path{chunker/entity_registry.py}):} Responsible for extracting and normalizing named entities (such as faculty names or course codes) from the generated Markdown documents. The module dynamically builds registries for faculty, courses, and programs, tracking aliases and assigning unique entity identifiers.
  \item \textbf{Semantic Chunker Module (\path{chunker/semantic_chunker.py}):} A content-aware segmentation framework that splits documents exactly at natural semantic boundaries rather than arbitrary character counts. It classifies each generated chunk into structural types (\textit{profile, regulation, table, section, list}), links extracted entity references, and enforces configurable word-count boundaries alongside SHA-256 deductive hashing to prevent index redundancy.
  \item \textbf{Knowledge Graph Builder Module (\path{knowledge_graph/builder.py}):} Constructs the phase-1 deterministic knowledge graph artifact (stored as JSON) by combining entity registries and chunk metadata. The module utilizes strict regex patterns and string heuristics to extract multi-relational edges (\textit{teaches}, \textit{part\_of}) and integrates an end-to-end provenance architecture where every extracted relationship retains a direct reference to its source chunk ID.
  \item \textbf{RAG Ingestion Module (\path{rag_ingestion.py}):} Handles the vectorization pipeline using the \textbf{EmbeddingGemma} 768-dimensional model via the \textit{Sentence-Transformers} library. The module caches embedding vectors to bypass re-encoding during rebuilds, and seamlessly initializes multiple isolated persistent collections inside ChromaDB (e.g., separating table-heavy content from general text).
  \item \textbf{Query Router Module (\path{rag_ingestion.py}):} The runtime layer that intercepts user prompts. It features an intent classification stage that categorizes requests across seven domain types, dynamically routing searches to the appropriate vector collection or to graph traversal, applying adaptive distance thresholds based on retrieval quality, and finally formatting context windows for LLM synthesis.
  \item \textbf{FastAPI Integration and End User Interface (\path{api_server.py} \& \path{chatbot.py}):} The serving layer exposing RESTful endpoints, including a \texttt{/chat} inference interface serving generative responses, and metrics diagnostics on \texttt{/stats}. This is fully integrated with a browser-based UI frontend supporting Markdown formatting, dynamically generated tables, and conversational cache support.
\end{enumerate}

\chapter{Conclusion and Future Work}

\section{Conclusion}

This mini project successfully developed and evaluated a Hybrid Knowledge-Graph-Enhanced Retrieval-Augmented Generation (KG-RAG) system tailored specifically for academic information access. By deeply processing decentralized, unstructured HTML and intricate PDF syllabus documents from the MBCET CSE department, the pipeline systematically synthesized an accurate, multi-relational vector database alongside a strict, deterministic declarative knowledge graph. Integrating a 768-dimensional local Gemma embedding topology with continuous semantic deduplication resolved significant discrepancies native to baseline lexical search models. Furthermore, complex structural queries securely mapped against high-confidence graph pathways (utilizing semantic mappings such as \textit{teaches} and \textit{part\_of}), ensuring responses were inherently grounded by algorithmic evidence and mitigating hallucinated predictions. The resulting hybrid framework efficiently bridges the semantic gap for multifaceted academic queries, offering an automated, dependable, and explainable chat interface explicitly primed for institutional applications.

\section{Future Work}

Although the active infrastructure substantiates the effectiveness of intent-aware multi-modal algorithms, meaningful evolution pathways persist for subsequent optimizations:
\begin{enumerate}
    \item \textbf{Expanded Prerequisite Constraints:} Incorporating recursive schema constraints (such as context-aware extraction bounded by nearby academic regulations) to comprehensively capture missing graph dependencies and elaborate multi-level prerequisite trees efficiently.
    \item \textbf{Operational Caching Strategies:} Transitioning the FastAPI runtime component to support query-result semantic caching mechanisms, fundamentally mitigating excessive Large Language Model API overhead experienced during traffic bursts common around examination schedules.
    \item \textbf{Relational Database Migration:} Migrating the locally generated phase-1 flat JSON repository directly into a specialized graphical Database Management System infrastructure (such as Neo4j). Such an enhancement inherently fosters the rapid graph traversal velocities critical when scaling the environment to support multi-department datasets across the wider university corpus.
\end{enumerate}
